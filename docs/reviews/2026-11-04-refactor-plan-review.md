## 1. 评审方法

1. **逐条复核**：对方案 §1 表中每一条 file:line 回到源码核对，并检查其"影响"一栏是否被代码事实支持。
2. **实测 A（后端）**：在临时 SQLite 上调用**真实** `persist_segments` / `record_audio_seq`，
   分别按"现状（每条一次）"与"方案方向（合并成一次）"计时，N 取 100/200/400/800。
3. **实测 B（前端）**：用 Node 复刻 `upsertSegment` 的既有索引路径（`:606`–`:634` 的 slice + sort + Map 重建），
   N 取 200/1200/3000，测单次开销。
4. **交叉检查**：全仓（不只 `backend/src`）检索跨平台危险调用、绝对路径、连接池配置、测试断言强度。

> **方法学提示（值得记入结论）**：本次实测的首版基准脚本缺失一个 `return`，
> 导致所有落库走异常兜底路径——**数字看起来完全合理**（0.6 s / 2.2 s / 4.5 s，还呈现平滑增长），

## 2. 阻断性问题

### 2.1 B-1：优先级排序不成立——实测反驳了方案的严重度模型

方案 §1 把 C-1（逐段落库 O(N²)）列为第一优先级，理由是"2 小时会议约 1200 段 → 约 144 万行扫描 + 1200 次全局写锁"，
并在 §2.1 称"整场总工作量 ≈ N²/2 行扫描"。**这条复杂度推理在数学上没错，但作为严重度陈述是错的。**

实测（§7.1，Windows / SQLite WAL / `synchronous=NORMAL`，真实代码路径）：

| N（单场段数） | 现状：每条一次 | 方案方向：合并一次 | 比值 | **现状的单次成本** |
|---|---|---|---|---|
| 100 | 0.196 s | 0.016 s | 12.0× | 1.96 ms |
| 200 | 0.379 s | 0.027 s | 14.1× | 1.90 ms |
| 400 | 0.820 s | 0.052 s | 15.8× | 2.05 ms |
| 800 | 1.851 s | 0.111 s | 16.7× | 2.31 ms |

**单次成本从 1.96 ms 只涨到 2.31 ms（N 涨 8 倍，成本涨 18%）**。也就是说：
二次项真实存在但被一个约 1.9 ms 的固定事务开销完全主导。按此推算 1200 段 ≈ **2.4 秒，
摊到 2 小时会议上是 0.03% 的占空比**。C-1 不是性能危机，是"落库节奏不卫生"。

C-2 同样被高估：400 次逐块 commit 实测 217 ms（**0.54 ms/次**），合并到 1/32 后 6 ms。
按 600 ms 一块的音频节奏，整场约 12000 次 commit ≈ **6.5 秒 / 2 小时 = 0.09% 占空比**。

前端 P-1 实测（§7.2）：N=1200 时 **0.109 ms/条 partial**，12000 条累计 **1.3 秒 CPU / 2 小时**。
方案称"末段每次 O(n log n)，明显掉帧"——**"明显掉帧"没有依据**：0.109 ms 是 16.7 ms 帧预算的 0.7%。

**要求的修订**：

1. 把 C-1 / C-2 / P-1 从"性能问题"改判为"写入节奏与代码卫生问题"，优先级降到 P3，
   并**删除**"144 万行扫描""明显掉帧"这类未测量的严重度措辞；
2. 保留这两项改动（仍值得做：缩短写锁持有时间、减少 WAL 抖动、让 `indexById` 名副其实），
   但**不能作为方案的主要卖点**——否则实施完成后无法证明任何收益，会损害方案本身的可信度；
3. **补一条边界条件**：结论对"单场千段级"成立。若单场段数上升一个数量级（万级），
   二次项会重新成为主项（N=800 时二次项占比仍 < 2%，N=10⁴ 时反超固定项）。
   方案应写出这个阈值，而不是宣称"全场景 O(N²) 灾难"。

### 2.2 B-2：漏掉了用户可见的跨平台缺陷（恰好在本方案的主轴上）

方案 §5.1 的结论是"代码层比预期干净"，据此把双平台工作收敛为"CI 门禁 + 运维脚本下沉"。这个结论**漏了一条**：

```python
# backend/src/imeeting/export/document_export.py:113
font_path = r"C:\Windows\Fonts\msyh.ttc"
try:
    pdfmetrics.registerFont(TTFont("MSYH", font_path, subfontIndex=0))
    font_name = "MSYH"
except Exception:
    font_name = "Helvetica"          # ← Linux 上必然走这里
```

- 生产部署是 `deploy/backend.Dockerfile`（`python:3.12-slim`），apt 只装了
  `curl / ffmpeg / libgomp1 / libsndfile1`（`:14`–`:17`）——**镜像内不存在 `C:\Windows\Fonts`，也没有任何 CJK 字体**；
- 因此 Linux 上 PDF 导出恒走 `Helvetica` 兜底，而 Helvetica 无 CJK 字形 → **导出的 PDF 中文不可读**；
- 现有测试**抓不到**：`tests/test_meeting_product_extras.py:343` 只断言 `pdf.content.startswith(b"%PDF")`。
  也就是说 CI 在 Ubuntu 上绿着，功能实际是坏的。

这是本方案在"Windows/Linux 都适配"轴上**最该发现的一条**，而它被漏掉了。相比之下方案花了整节篇幅讲
"Windows 上的文件锁语义"（且自己标了 [未实测]）。

**要求的修订**：在 §5 增列该项，处理方式建议：

1. 字体按候选列表探测（`FONT_PATH` 环境变量 > 系统 CJK 字体 > reportlab 内置 CID 字体 `STSong-Light`）；
2. 镜像内加装 `fonts-noto-cjk`（体积约 60 MB，需权衡）或明确要求挂载字体目录；
3. 补一条**能失败**的测试：断言 PDF 内嵌字体不是 `Helvetica`，或对含中文的导出产物做文本抽取校验。

### 2.3 B-3："`stream.py` 与测试不需要同步改"不成立

方案 §4.1 的验收约束写："`StreamSession` 的公开 API 保持不变，`stream.py` 与测试不需要同步改（降低回归面）"。
核对代码：`stream.py` 已经在调用**私有**成员——

```
359: await session._finalize_current(force=True, reason="user")   # partial_hint 控制消息
623: await session._emit({...})                                   # 会议元信息推送
670: await session._emit({...})                                   # 渐进纪要推送
```

拆分时这三处必然要改（且 `_finalize_current` 应由"用户主动切句"这一外部事件驱动，本身就该是公开方法）。
**要求的修订**：把验收条件改为"先把这三处提升为公开方法并加测试，再做拆分"，
并补充"拆分后 `stream.py` 的改动行数应 < 20 行"这类可判定口径。

### 2.5 B-5：缺少安全不变量约束

方案要动 `settings.py`（Fernet 加密的密钥类配置、`_decode_secret` 降级路径）、配置写回（`persist_config`）、
`session_writer`（新的集中写入点）。这些位置直接关系：

- 密钥**不以明文**回传给前端（`snapshot(redact=True)`）；
- 解密失败时**降级为空串而非密文**（`settings.py:1692` 的既有决定）；
- 审计哈希链（`audit.py` 的 `prev_hash`/`record_hash`）写入顺序不能乱；
- 分享令牌**只存摘要**。

重构 `settings/` 与写入路径时，这些是**不变量**，不是实现细节。方案通篇没有"安全不变量清单"，
也没有"重构后必须仍然成立的断言"。**要求的修订**：在 §4 前加一节"不变量与必须保持的测试"，
至少覆盖：密钥脱敏、解密降级、审计链顺序、令牌摘要、权限矩阵（`deps.py`）。

## 3. 重要问题

### 3.1 M-1：P-4 的因果细节错误

方案称泄漏的线程"含模型句柄引用"。核对 `engine/pool.py:71`–`:78`：旧 `ThreadPoolExecutor` 的 worker 线程
阻塞在**空队列**上，不持有任何模型对象（模型的引用在 `_models` 字典里，与线程池无关）。
真实后果是**线程泄漏**（每次改 `asr.infer_threads` 或 `session.max_concurrent` 泄漏 N 个常驻线程），
仅当旧池里当时还有排队任务时才会短暂持有闭包引用。**结论方向对，因果链写错**，需修正，
否则实施者会按错误模型去验证（比如断言内存里模型被重复加载，这是测不出来的）。

### 3.2 M-2：连接池被完全忽略（实测已确认这是真实风险面）

方案没有任何一处提到 SQLAlchemy 连接池。实测输出：`pool: QueuePool | pool_size: 5`。
SQLAlchemy 2.x 对文件型 SQLite 默认 `QueuePool(pool_size=5, max_overflow=10)` → **上限 15 条连接**，
而并发方来自：FastAPI/anyio 线程池（默认 40 线程）跑同步 `def` 端点、`asyncio.to_thread` 的落库调用、
2 条 job worker、音频/清理线程。**满载时可能出现 `QueuePool limit ... connection timed out`（默认 30 s）
→ 500 与请求堆积**。这比 C-1 的 2.4 秒更值得先处理，而且它是"稳定"轴的直接内容。

**要求**：`create_engine` 显式配置（`pool_size` / `max_overflow` / `pool_timeout` / `pool_pre_ping`），
并与 `session_writer` 的单写者设计联动（单写者天然把并发连接压到 1–2 条）。

### 3.3 M-3：R-1 的工作量被显著低估

`StreamSession` 1283 行、约 90 字段；`backend/tests` 里有 `test_streaming_engine.py`、`test_stability.py`、
`test_ws_protocol.py`、`test_persistence_race.py`、`test_field_log_fixes.py` 等多个文件直接或间接依赖它的内部状态
（例如 `session._pending_tasks`、`_metric_pending`、`_finalize_current`）。方案给 3–5 天，**不现实**；
且"先提取组件、保持公开 API"的策略与 B-3 冲突（私有成员已被外部使用）。

**要求**：把 R-1 单独列为"重构轨道"，给出前置条件（先补 3 处公开方法 + 特征化测试 characterization tests），
并按"组件级可独立回滚"拆成 4–6 个 PR，而不是一批。

### 3.4 M-4：X-1 的验收口径可被"全部 skip"绕过

方案承认 Windows CI"首次引入会有既有失败"，缓解措施是"先用 `continue-on-error` + 失败清单，逐个修"，
但 §7.3 的通过标准只写"PR 里出现 Windows 的 backend + frontend 两个绿勾"——**跳过所有失败用例同样算绿**。

**要求**：把标准改为"Windows 上**实际执行**的用例数 ≥ Linux 的 95%，跳过清单必须有原因与到期日并只减不增"。
另需注意一个有利事实：CI 现在就是 `pip install -e ".[dev]"`（**不含 `[asr]`**），说明测试套件不依赖 torch/funasr，
Windows 上跑得通的前提已具备；预期失败会集中在文件锁/路径/时区/浮点格式，应在方案里列出预期清单而不是笼统表述。

### 3.5 M-5：C-2 的"行为不变"依赖了一个无界结构

方案称 C-2 合并写"行为不变"，因为服务端按 `seq <= audio_chunk_seq` 幂等丢弃多发的块。
但前端 `preReady`（`frontend/src/api/ws.ts:45`）当前**无上界**，而方案在 P-4 才提"给 `preReady` 加上界"。
两处需联动：先加上界，再放宽服务端的持久化节奏，否则极端情况下补传量会被放大。

### 3.6 M-6：缺"批次 0：先测量"

方案的 §7.2 自己列了 4 个"需要新增的度量"，并承认"否则优化无法证伪"。既然如此，
**度量本身就该是第一批**，而不是放在验收章节。本次评审已经证明这一点：不做测量，方案会把 2.4 秒的问题写成头号问题。

### 3.7 M-7：平台断言缺少置信度标注

§5.4 写"`uvicorn[standard]` 在 POSIX 上用 uvloop，Windows 用 asyncio **Proactor**"。
uvloop 部分确定；**Windows 上 uvicorn 实际使用的事件循环策略（Proactor 还是 Selector）未经核实**，
不同版本行为不同。这类断言应标 [待核实] 或给出核实方法（`asyncio.get_running_loop()` 打印类名）。

### 3.8 M-8：没有定义回滚机制

方案反复说"每批可独立回滚"，但最危险的两项（`SessionWriter`、`StreamSession` 拆分）改动的是
**写入路径与会话状态机**，出问题时的表现是"会议数据缺段/状态卡住"——`git revert` 无法回滚已经写入的数据。
**要求**：为这两项定义灰度方式（例如 `session.writer_enabled` 配置开关 + 双写比对日志 + 一个回滚演练脚本）与
数据修复路径（`segment_count` 校正、会话状态收口）。

## 8. 未验证边界

1. **未在 Linux 上运行任何东西**。§2.2 的 PDF 字体问题是"代码事实 + 镜像事实"的推断：
   `C:\Windows\Fonts` 在 Linux 不存在、镜像未装 CJK 字体、兜底 `Helvetica` 无 CJK 字形——
   结论方向确定，但**导出的具体表现（缺字/方框/问号）未经目视确认**。
2. **P-2（每条 partial 强制回流）的真实成本未测**。本次只证伪了 P-1 的"明显掉帧"，
   不能反推 P-2 也无害；它需要在真实浏览器 + 长转录（1000+ 卡片）下用 Performance trace 量化。
3. **连接池耗尽（M-2）未压测复现**。`QueuePool(5+10)` 是实测的池类型与大小，但"是否真的会耗尽"取决于并发路径，
   需要用 `scripts/stress.py --only concurrency` + HTTP 混合负载复现。
4. **Windows CI 的预期失败清单未实测**（§3.4 只给出方向）。
5. 后端 765 项测试、前端四项检查本轮**均未运行**——本评审只做静态核查与两处定点实测。
