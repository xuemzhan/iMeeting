## 两份需求的衔接

```text
会中口述「这位是总体院的张主任」
        │
        ▼  REQ-001：LLM 抽取姓名/单位/职务 → person + person_attribute + meeting_participant
        │
        ▼  REQ-001：人工确认 → 绑定 speaker_key ↔ person
        │
        ▼  REQ-002：该人跨场景的声纹样本聚类 → ≤5 条场景模板 → 正式库（人工确认过才入）
        │
        ▼  REQ-002：新样本确认时评估「与本人差异大 / 更像别人」→ 三选一提示
```

- 身份主键统一到 `person`；`voiceprint` 只是“这个人怎么被听出来”的实现细节。
- REQ-001 负责“他说他是谁”，REQ-002 负责“这个声音是不是他”；两者冲突时**以人工确认为准**，并同时记审计。
- 两份文档的 §7 数据模型、§8 接口草案、§12/13 验收标准按同一套术语书写，可直接用于拆分开发任务。

## 评审时需要的三个决定

1. 人员本体与声纹模板是否按 `owner_id` 隔离（当前草案：是，与现有 `voiceprint.owner_id` 一致）；
2. `person` 与 `voiceprint` 的合并排期（草案：REQ-001 P0 先建 `person`，REQ-002 P1 把 `voiceprint.person_id` 补上，中间用 `name` 过渡）；
3. 冲突提示的打扰强度（草案：高冲突阻塞、其余非阻塞，同组合两次接受后不再打扰）。
